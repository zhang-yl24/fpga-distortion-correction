# stable30 上板交接与帧率验收

本轮目标是固定纯校正模式下，稳定接近每秒 30 个新校正帧。候选为 `both + corrected`，`param_id = 8c73465e`，输入与输出沿用 **1920×1080、29.97/30 Hz** 路径，Gamma OFF、零旋转。当前参数仍随封存工程绑定；接入真实镜头 K/D 后需要重新构建、取得新的身份并复测。本候选尚未板测，稳定 30 FPS 的结论等待以下实测记录。

位流文件名为 `both_corrected_8c73465e_DIAGNOSTIC_NOT_TIMING_SIGNOFF.sbit`。它的目录位置、SHA256、最终双角 STA 和未签核项目以本次完整包的 `START_HERE.md`、位流状态文件及构建回执为准；文件名保留诊断标识。此前 baseline/both/cache 包的构建入口与位流对应不同候选。

**1. 保留回退，再核验本次输入与位流。**

保留同学现场已验证的旧演示 bit、配套源码/参数、SHA256、下载方式及恢复步骤，单独放入回退目录。此前新生成且尚未上板的 baseline/both 位流仍需各自验证。新候选放在独立目录，沿用已经成功的板卡、供电、HDMI 线、显示器和下载流程。

完整 ZIP 先执行其根目录 `START_HERE.md` 的核验入口。在仓库的 `delivery/20261103-hdmi1080-stable30` 目录可运行：

```powershell
python -B tools/verify_candidate.py
```

核验通过后核对位流回执中的 `param_id` 为 `8c73465e`，记录实际下载文件的 SHA256。电脑固定输出 1080p29.97；如果改用 30.000 Hz，单独记录这一条件及输入准入状态。保留显示设置截图和实际输入时序记录，避免把已打通的 1080p60 显示路径混入本次测试。图像使用带运动和细节的固定测试片段，例如运动棋盘、文字或滚动计时器；同时留一段真实镜头画面便于观察清晰度与畸变效果。

本版上电即为纯校正，扫描包应为 `mode=1`。约三秒原图/校正切换属于演示模式，其结果单独保存。沿用现场已验证的 b4 LOAD/ARM 与原始 UART 采集流程，并将接收端构建身份白名单更新为 `8c73465e`。session ID 使用本次会话的真实非零 nonce，每次复位或重新采集启用新会话。本包的分析脚本只读取文件，未提供串口采集或控制命令。

**2. 先进行 60 秒预检。**

待 HDMI 锁定、DDR 初始化和画面稳定后，预热至少 10 秒。随后开始独立的 60 秒采集窗口；预热与 LOAD/ARM 等待时间单独记录。主机使用单调时钟记录接收窗口起止时间，保存逐字节原始 UART 二进制及实际秒数。开始新窗口前按原采集程序处理旧接收缓冲，避免把上一会话的数据算入当前窗口。

分析命令在 stable30 候选目录执行。以下 `60.066112` 和 `12345678` 仅为格式示例，必须替换为该文件对应的真实时长、真实 session ID：

```powershell
python -B tools/analyze_scan.py D:/capture/stable30-precheck.bin --seconds 60.066112 --param-id 8c73465e --session-id 12345678 --output D:/capture/stable30-precheck.json
```

输入文件应为原始接收字节；十六进制文本、终端打印和录像不能直接传入该脚本。`--seconds` 必须包含保存该字节文件的完整接收窗口，不能直接填计划值 60，也不能用包数除以标称 30 Hz 反推时长。

| JSON 字段 | 本次判读方法 |
| --- | --- |
| `valid_fixed_correction_window` | 必须为 `true`，同时检查 `issues` 为空。 |
| `accepted_unique_display_fps` | 窗口内不同完整扫描 `frame_id` 的个数 ÷ 实际秒数；这是本轮主要帧率指标。 |
| `observed_scan_records_per_second` | 完整数字扫描记录数 ÷ 实际秒数，包含重复显示。 |
| `repeat_scan_records`、`repeat_fraction` | 相同帧 ID 的重复扫描数量与比例；重复扫描不增加唯一帧数。 |
| `signature_sequence_gap_events`、`scan_epoch_gap_events` | 均应为零；缺包或缺扫描会使当前统计无法作为有效验收。 |
| `trailing_partial_packet_bytes` | 固定接收窗口可能截断最后一个包；单独记录，脚本只统计完整包。 |

脚本核验 PGSIG001 包 CRC、格式、session/param 身份、固定纯校正模式、1920×1080、每帧 2,073,600 像素、采样 mask，以及帧 ID/CRC 一致性。有效期内同一帧 ID 的 CRC 改变、帧 ID 倒退、观察器错误等会使 `accepted_unique_display_fps` 为 `null` 并返回失败。保留错误原始数据，修正采集或硬件问题后建立新的窗口。相邻不同帧 ID 的 CRC 相同可以来自静态画面，不能仅靠 CRC 去重。

例如输入 29.97 Hz 时，60 秒理想约有 1,798 个新帧；一次窗口边界可能相差约一帧。完整扫描接近 30 次/秒但唯一帧只有 23 个/秒，说明仍存在重复显示。新帧指标必须依据完整扫描里的不同帧 ID 统计，输入帧 ID 的最大值减最小值会把中间跳过的帧也算进去。

**3. 预检通过后连续运行至少 10 分钟。**

重新建立会话，保持同一输入模式、线缆、参数和测试内容，记录至少 600 秒的完整原始字节文件与真实起止时间，再用同一命令分析。该命令中换成正式文件、实际秒数和正式 session ID。中途复位、输入模式改变或重新 ARM 时结束当前窗口，分别保存各段，重新完成预热后再计时。

建议本轮团队工程验收门槛为：有效纯校正窗口成立；唯一帧率达到输入有效帧率的 99% 以上（29.97 Hz 时约 29.67 FPS，30 Hz 时约 29.70 FPS）；重复扫描比例不高于 1%；画面无黑屏、撕裂、持续停帧；已取得的故障/欠载/溢出计数无新增。此门槛用于本轮调优，竞赛评分仍按赛题要求核对。正式报告填写实测值，保留 29.97 与 30.000 的区别。

主机若能保存带单调接收时间的原始包记录，再检查连续 60 秒分窗有无随时间下降或成片重复。当前 `analyze_scan.py` 接收一个二进制文件和一个真实总时长，未实现带时间戳分窗；缺少时间戳时先报告完整 10 分钟平均值和可见异常，避免用“每 1,800 包”代替一分钟。正式测试不应通过删除慢段或错误段提高结果。

**4. 把显示结果与内部等待分别记录。**

现有扫描协议没有传输内部处理周期，也没有通用 UART 寄存器读取命令。扫描包中的 `dropped/aborted/malformed` 是遥测观察器计数，不能当作 HDMI 输入 DMA 的丢帧、FIFO 溢出计数。以下信号若已通过现有调试接口或逻辑分析仪取得，保存同一窗口起止快照及增量；未取得的项目明确填写“未测”，不要填零。

| 内部信号 | 作用与口径 |
| --- | --- |
| 输入有效 SOF/准入/时序告警 | 判断输入节拍、初始化及受控消隐告警；本版未保证这些计数都已导出。 |
| `captured_frames` | DMA 完整源描述符被处理器接受时递增；不等于摄像头或 HDMI 的 SOF 总数。 |
| `processed_frames` | 引擎完成且源/结果事务已排空后的处理完成计数。 |
| `presented_frames` | 控制器确认成功扫描的新帧数量；与主机唯一扫描统计可互相核对。 |
| `last_process_cycles` | 最近一帧从源描述符接受到引擎完成的 core 周期，未包含接受前的源帧排队时间。按实测/回执确认的 core 频率换算；本构建为 125 MHz 时，毫秒数为周期数 ÷ 125,000。 |
| `processing / pending / display_active` | 判断引擎忙、结果等待显示、显示占用；单次快照不足以代表整个窗口的占空比。 |
| `no_free_frames / dropped_frames / overflow_frames` | 输入 DMA 缺空闲源缓存、丢弃和 FIFO 溢出；分别记录增量，避免相加重复计算一次故障。 |
| `underflows / mismatches`、`failed / fault` | 输出欠载、校验异常及失败状态/故障码。 |
| DDR 初始化/复位恢复状态 | 记录上电、复位至重新出图的时间和结果；已有状态接口可见的字段随日志保存。 |

若需要增加内部观测，使用独立诊断构建，在 core 域锁存被动快照并带帧 ID，再按既有保持握手跨域输出。新增 RTL 会产生新的构建身份与时序结果，应单独验证。旧仿真处理时间、扫描刷新率和主机采集时长均不能代替板上处理延迟。物理端到端延迟另外测量。

**5. 检查冷启动、复位及回退。**

10 分钟稳定窗口之外，按板卡既有操作规程完成至少三次冷启动、三次按键/全局复位恢复。逐次记录是否完成 DDR 初始化、恢复有效画面所需时间、是否需要再次人工操作，以及故障状态。每次重启帧 ID/计数器会重新开始，应使用新 session；这些短恢复测试单独归档。厂商 DDR 时钟关系约束已恢复到候选工程，其物理复位恢复仍由这组实测确认。

如出现持续黑屏、撕裂、停帧、DDR 初始化失败或错误增长，先保存当前原始 UART、时长、输入设置、故障码和短录像，再按原封存流程加载已经现场验证的旧演示 bit。恢复旧输入配置与旧参数，确认演示重新正常。候选失败段和回退记录一并保留，便于定位输入、复位、处理或显示环节。

**6. 三源缓存与最小回传材料。**

本版有三个源缓存和两个结果缓存。`BANK_STRIDE=1048576` 的单位是 4 字节；每个物理槽间隔 4 MiB。地址映射如下：

| 逻辑用途 | 物理 DDR 槽 | 字节起始地址 |
| --- | ---: | ---: |
| 源 bank 0 | 0 | `0x00000000` |
| 源 bank 1 | 1 | `0x00400000` |
| 源 bank 2 | 4 | `0x01000000` |
| 结果 bank 0 | 2 | `0x00800000` |
| 结果 bank 1 | 3 | `0x00C00000` |

物理槽 4 为新增 4 MiB 源缓存，地址窗口覆盖前 20 MiB。源 bank 元数据为两位，源所有权掩码为三位。扫描包 `bank` 仍表示两个结果缓存，合法值保持 0/1；看到扫描 `bank=0/1` 不能推断第三源缓存没有工作。核心文件头部遗留的“四个 DDR banks”注释描述旧布局，本表及候选地址逻辑定义当前五槽布局。缓冲增加可降低相位等待造成的丢帧，持续处理超过单帧预算时仍需继续优化。
