# 后续发布流程

## 固定目标

默认工作是 HDMI 摄像头 1920×1080、标称 60 Hz 输入，KEY1 选择 RAW/CORR，不另加旋转。当前 AA 默认 CORR、Gamma OFF。更改默认目标时须在项目索引和版本说明中明确记录，不把旧模式隐式恢复进来。

输入/扫描 Hz、新呈现 FPS、处理耗时和端到端延时分别报告。内部 STA、仿真、依赖闭包、重新构建和实板结果分别列状态；未运行写“未运行”，不从旧版本借结论。

## 不再一交付一分支

- main 是共同入口和经过核验的组织/收录主线。
- 当前摄像头/KEY1 的后续补充复用 `delivery/20261107-camera1080p60-key1-aa`。日期旧不构成再建一条日期分支的理由。
- 同学 directfill 与三个开放 PR 保留各自工作线和依赖。不要为减少数字关闭他们的事项或改写历史。
- 发布版本用不可变标签与发布清单表达，例如 `candidate/camera1080p60-key1/<版本>`；经过同版现场验收后才能使用表示已验收的发布名称。
- 仅在确有独立并行工作且需要隔离时建立短期功能分支，先说明目的、归属和结束条件；完成合入和保全后收掉临时分支。不要为文件打包、更新说明或补一份报告另建分支。

以上是后续用户要求发布时的组织方式，不是授权自动关闭他人的 PR、上传受限依赖或擅自运行硬件。

## 文件放置

1. 继续使用当前交付目录补充它的重建、验证和操作说明，不把同一源码散落到根目录或再造一套“最新”副本。
2. 更换实际源码、参数、约束或位流时创建可追溯版本，保存原发布标签；同步记录源 SHA、工具/IP版本、输入闭包、位流 SHA256 和验证边界。
3. 在 `docs/PROJECT_INDEX.json` 更新默认候选固定 SHA 与入口，在 `docs/PROJECT_MAP.md` 记录与前版关系。文件清单按新固定头重新生成，而非从分支名称猜版本。
4. 现有冻结目录的 Tcl/include/manifest/verifier 路径保持不动。若必须迁移，先保全旧树，明确全部引用和校验器变更，在独立副本验证后发布迁移版；不能只移动目录然后沿用旧“校验通过”结论。
5. 厂商 IP/PLL 与许可证仅按合法权限处理。公开配置说明不等于可重新分发受限实现；缺输入时检查明确失败，不加占位模块绕过。

## 发布前核对

- 刷新远端 head、开放 PR 和同学正在工作的分支。不要覆盖新提交、未提交工作或活动构建目录。
- 核对默认摄像头格式、KEY1 语义、无新增旋转、Gamma状态、器件与引脚。模块旧名称不代表实际选中配置。
- 对可执行源码改动运行对应离板测试；对文档/清单改动核对链接、行数、哈希和完整覆盖。记录未运行的阶段。
- 原生构建按具体包的官方工具步骤串行运行，使用新输出目录。新 IP、PLL、约束或参数必须重新实现并核对时序；不能沿用已有 sbit 的3 ps余量。
- 实板测试另行遵守硬件操作授权及回退要求，固定同版位流和遥测身份。显示器“60 Hz”不能代替新帧率验收。
- 正常非覆盖提交，核对期望远端 head。与他人提交冲突时重新整合，不强推。
- 读回远端提交、产物和最终 CI，再更新项目入口。PR 保持草稿直到对应验证条件满足，不把归档作为硬件验收。

## 结束一条工作线

先确认无开放 PR head/base、正在工作的人或外部依赖，再建立归档标签并读回 commit/tree，保存原分支名、SHA与恢复方法。最后带精确 head 保护移除旧远端名称。本地分支和工作区不随远端整理删除。

从归档恢复时先确认同名分支不存在，核对标签指向的原完整 SHA，再创建同名远端分支；同名已被他人重建时不覆盖。Git 标签保全已提交内容，不是缺失厂商输入或外部资产的备份。
