# 1080p30输入路线与吞吐核定（FPGA-1027-D）

本轮结论：**现有8bit、单沿DVP、RGB565两拍路线不能规格内输入原生1080p30。最短的原生1080系统输入候选是板载MS7200 HDMI接收；若要求同一鱼眼摄像头原生1080，则RAW Bayer8是有条件候选，必须增加去马赛克/颜色处理。两条输入路线均不能绕过现主版的大角度写回吞吐与1080计数器限制。** 720p30仍是当前相机RGB565路线的短路径目标。没有采购结论，也没有新硬件实测。

本轮仅离板资料/源码核对、主机关键修复及模拟生命周期测试。未运行PDS或整体RTL仿真，未启动下载器/访问JTAG或串口、未采图或写Flash；B封存RTL/私参/约束/bit及构建助手不变。下列预算是算术和源码边界，不是实测FPS、DDR效率或30fps承诺。

## 1. 准确设备和输入规格

项目板卡资料对应MES2L676-100HP（盘古100Pro+）、PG2L100H/FBG676；当前替换模组的OV5640型号由操作员声明及既有SCCB ID=0x5640佐证，不代表已独立核验商家SKU、镜头真实FOV或MIPI布线。用户本轮已明确确认：同一采样模组、CAM2接口/40针方向/FPC锁扣未变、未调焦，外接电源正常、无异常发热、本人可立即断电。这是现场声明，本轮没有扫描身份、测电压或读取温度。

现B顶层 `board/corrected_gamma_pipeline_d5.v:3` 为8位cam_data，接收器 `rtl/dvp_rgb565_capture.v` 在posedge采样，两字节合成16bit。B实际使用 `ov5640_cadence_trial_init`，当前寄存器表 `board/ov5640_cadence_trial_commands.vh` 为0x4300=6F、0x501F=01，即RGB565/ISP RGB，不是RAW8。原始配置必须连同PLL、HTS/VTS、采样极性和IO约束审查，不能只改两个格式寄存器。

| --- | ---: | ---: | --- |
| RGB565，8bit两拍 | 124.416MHz | 168MHz | 超出并行96MHz额定，否决当前路线 |
| YUV422，8bit两拍 | 124.416MHz | 168MHz | 换成YUV422不能解决带宽 |

依据为本地OVT原版手册v2.01（177页）PDF166、§8.4表8-5：parallel fPCLK typ48/max96MHz。脚注d/e说明典型模式、全幅RAW/YUV及MIPI建议；不能把脚注理解成所有RAW只能15fps。PDF22的“1080p30、96/192MHz”没有区分接口/格式，不能覆盖表8-5或推翻两拍字节预算。PLL VCO上限800MHz见PDF25；当前载板/IO在96MHz是否可靠也未验证，额定上限不是已签核采样频率。

OVT手册PDF86表6-5规定0x4300=00..03为RAW及不同Bayer顺序；PDF74表5-11及PDF140表7-21规定0x501F低3位=3为ISP RAW(DPC)。这是格式依据，不是可直接下载的完整1080p30配方。必须核8bit输出选择、真实CFA顺序、曝光改变帧长、24/27MHz XVCLK、PLL与逐行/逐帧监测。

[Linux官方v6.6源码](https://raw.githubusercontent.com/torvalds/linux/v6.6/drivers/media/i2c/ov5640.c)第190–254行给出RGB565/YUV422 2X8与RAW Bayer8 1X8；1018–1038行为1080 DVP时序，1498–1534行为PCLK计算。驱动能算出168MHz不代表传感器获得超规格许可。本地手册SHA256为 `c314bd8cbae376e1ea215b20501dcbe9ba86777d359ef7f1f2f9c807b41bf4d1`；[同版OVT原稿公开镜像](https://files.waveshare.com/upload/d/da/OV5640_DataSheet.pdf#page=166)可复核。OVT官网产品页本次工具不可访问，未声称已据官网确认额外能力。

原参考载板 `DOUBLE-DVP-OV5640-1113.pdf` 的40针确有MIPI复用网络，不能说“完全未引出”；但尚无替换模组差分阻抗/长度/连接器、FPGA DPHY/CSI接收和引脚约束证据，当前123源链只有DVP。MIPI先列未验证路线，不据宣传页采购或承诺直接接入。

## 2. DDR容量与共享带宽

板卡手册给出2颗XCCC256M16EP-EINAY，各4Gbit/512MB，合计8Gbit=1GiB、x32总线。实际DDR IP配置选中MT41K256M16XX、row15/col10和1000MT/s；模板base项MT41K128M16XX不是实际选中容量。UI为125MHz×256bit，对应物理CK500MHz、x32 DDR，**共享理想峰值4.0GB/s**，尚无本轮持续可用效率eta的测量。

RGB565单帧=4,147,200B；RAW8单帧=2,073,600B。现主版BANK_STRIDE=262144的单位是4B地址字，即1MiB，不能直接装1080 RGB565。若沿现2的幂划分，改为4MiB/银行（参数1048576个4B字）；两输入+两结果共保留16MiB，可容入1GiB。四帧有效数据共16,588,800B。容量足够不表示现地址/计数/仲裁已经适配。

下面MB/s均为十进制，DDR只按有效数据计算，未计刷新、换向、bank冲突、仲裁等待或突发空隙：

| 通道（RGB565） | 1080处理30帧/s时 |
| --- | ---: |
| 摄像头/HDMI采集写输入 | 124.416MB/s |
| 写矫正结果 | 124.416MB/s |
| 读显示，输出30Hz | 124.416MB/s |
| 读显示，输出60Hz（包含重复帧） | 248.832MB/s |
| 除映射源读外合计，显示30/60Hz | 373.248 / 497.664MB/s |
| 四邻域各2B的有效tap载荷，无跨像素复用 | 497.664MB/s |
| 四tap载荷加其他流，显示30/60Hz | 870.912 / 995.328MB/s |

四tap载荷不是实际DDR流量或不可再降的下界：缓存复用可减少读量，突发填充和冲突会放大它。当前compact缓存arlen=7，每次8个256bit beat=256B；miss_count在每次填充时增加。令M为每个处理帧的真实cache fill次数，则源读=256×M×Fproc。总预算必须满足：

`B_capture + B_result + B_display + 256*M*Fproc <= eta*4e9 B/s`

eta未知，不能把4GB/s全部分配给像素。1080p30且60Hz显示时，理论eta=1也只能允许平均fill/output_pixel≤0.21993；若仅举eta=0.5的敏感性例子，则≤0.09434（约每10.6个输出像素最多一次fill）。这不是测得效率。最坏每输出像素4次256B填充达63.701GB/s，仅源读已远超总线，所以必须取得真实访问局部性和命中率。不能只说“DDR有4GB/s，所以够”。

## 3. 处理周期及现有硬限制

1080p30需要62.208M输出像素/s。125MHz下每帧总预算4,166,666.7周期，平均2.00939周期/输出像素，包含映射、缓存等待、插值、Gamma、写回和排空。

- A的DA07 VGA真实来源仿真最坏2,565,884周期/307200像素=8.35249周期/像素；它不是1080估计，更不是板上FPS。分辨率、旋转局部性和缓存冲突均会改变成本，不能作性能达标外推。
- `rtl/ddr_video_output.v:24` 的requested_words只有16bit；1080 RGB565需129600个256bit beat，超过65535，会回绕。新target至少17bit，并需覆盖边界/请求停止/CRC及跨帧排空；只改WIDTH/HEIGHT不够。
- `rtl/experimental/ddr_adaptive_result_writer.v:35` 只在COLLECT接收。tile分支先收N像素，再以READ/PACK两拍逐像素处理，尚不能与接收重叠。因此仅这三段至少3N=6,220,800周期=49.7664ms/1080帧，已超33.333ms预算；还未算DDR写和缓存等待。这是代码结构下界，不是测得帧率。
- use_tiles在abs(sinQ22)>1048576时触发。现host默认0°/13.25°/181.125°均走raster，不能用这三角测试掩盖大角tile吞吐。后续1080验收必须包含tile分支和跨阈值角度。
- 1080需要完整尺寸/地址/计数/显示时序的新配置。现720容器中居中的VGA画面、HDMI刷新频率、上采样输出均不算原生1080处理。现输出720时序约74.25MHz；1080p30也可为74.25MHz但HT/VT/有效区不同，1080p60则通常148.5MHz，后者还需新PLL和像素域时序/CDC签核，不能把所有1080一概写成148.5MHz。条带RAM也由VGA的10KiB增至1080的30KiB，若双buffer还须另算资源。

因此1080p30的真正处理前置里程碑是：在独立target解决显示计数和bank布局，并使tile接收/重排/CRC/DDR打包能流水或双buffer重叠，给缓存等待留出余量。不能仅换输入、加大DDR或改PCLK后立即宣称整链30fps。缓存每次fill还要串行SCATTER64拍；仅这段开销就要求1080p30平均fill/output_pixel≤2.00939/64≈0.03140，尚未给其他阶段留周期。DDR字节预算与core周期预算必须同时满足。
